Outlines the default error response schema, and some common error types.

## Error

Default response schema for 4xx and 5xx HTTP status codes.

### Table

| Parameter | Type                                       | Description          |
| --------- | ------------------------------------------ | -------------------- |
| status    | [integer](/protocol/types/numeric#integer) | The HTTP status code |
| message   | [string](/protocol/types/string#string)    | The error message    |
| errors    | [array](/protocol/types/other#array)       | The errors           |

### Usage

Here's an example of how to use the `Error` response within an API operation:

```typespec
import "@common-grants/core";
import "@typespec/http";

using TypeSpec.Http;
using CommonGrants.Responses;

model TestModel {
  id: string;
  name: string;
}

@summary("Get test")
@doc("Get a test model")
@get
op getTest(): OkT<TestModel> | Error;
```

## Common Error Types

The following error types are commonly used. From v0.6.0 each one also carries version response headers, declared in `Headers.VersionResponse` or `Headers.VersionResponseAuth`, or, for `BadRequest`, inline with `Headers.VersionLifecycle`. `CG-Version-Served` reports the full protocol version the response was served in. It is optional on 401 and 403 responses, because authentication can run before a version is selected, and on `BadRequest`, because the version errors share its status. The optional `Vary`, `Deprecation`, `Sunset` and `Link` headers come from `Headers.VersionLifecycle`. See [Versioning](/protocol/versioning) and the [Versions](/protocol/specification#versions) section of the specification.

### Version errors

From v0.6.0, a request whose `CG-Version` value can't be served gets one of four version errors. They carry no version response headers. Their schemas are on the [Versioning](/protocol/versioning#version-error-schemas) page.
