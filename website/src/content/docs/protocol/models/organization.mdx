## OrgRelationships

An organization's relationships to other organizations, added in v0.5.0 per [ADR 0030](https://github.com/HHS/simpler-grants-protocol/pull/1265) (draft). Each named list holds relationships of one category and direction, and `otherRelationships` holds connections outside those categories, which need not have a direction. Every list is optional, list order carries no meaning, and a provider can state a relationship from whichever organization's record it maintains. The protocol doesn't require reverse entries, complete lists, or agreement between the two sides. A relationship confers no authority over the other organization. See [Organization relationships](/guides/organization-relationships/) for worked examples.

| List               | Entry                                                   | Each entry says                                                     |
| ------------------ | ------------------------------------------------------- | ------------------------------------------------------------------- |
| parents            | [OrgHierarchyRelationship](#orghierarchyrelationship)   | `org` is above this organization                                    |
| children           | [OrgHierarchyRelationship](#orghierarchyrelationship)   | `org` is below this organization                                    |
| succeededBy        | [OrgSuccessionRelationship](#orgsuccessionrelationship) | `org` carries on all or part of this organization                   |
| succeeds           | [OrgSuccessionRelationship](#orgsuccessionrelationship) | This organization carries on all or part of `org`                   |
| recordReplacedBy   | [OrgRecordRelationship](#orgrecordrelationship)         | `org`'s record should be used instead of this record                |
| recordReplaces     | [OrgRecordRelationship](#orgrecordrelationship)         | This record should be used instead of `org`'s record                |
| otherRelationships | [OrgOtherRelationship](#orgotherrelationship)           | This organization is connected to `org`, possibly with no direction |

When a list is absent the publisher did not provide it, an explicit `null` asserts it does not apply ([ADR 0024](https://commongrants.org/governance/adr/0024-optional-field-nullability/)), and an empty array is a present, empty list. The schema validates shape only: it doesn't check whether the other organization exists or whether two records agree.

The schemas write `relationships` on [OrganizationBase](#organizationbase), and an entry's `kind`, `startDate`, `endDate`, and `status`, inline rather than as references, because OpenAPI 3.0 cannot mark a reference as nullable. In the OpenAPI 3.0 document, `status` also lists `null` among its `enum` values, since OpenAPI 3.0.3 applies `enum` to `null` as well.

## OrgHierarchyRelationship

A parent or child relationship, added in v0.5.0. Every relationship list uses the same entry shape, defined once as a template; the entries differ only in the standard subtypes `kind` accepts.

- `org` is required and is an [OrgRef](#orgref). In a [patch](#orgpatchdata), `org.id` is writable and `name` is optional, so a writer can name the other organization by `id` alone. Validation doesn't fill in the `name` or `identifiers`.
- `kind` is optional. It is an [extensible enum](/protocol/fields/extensible-enum/) whose `value` is one of [OrgHierarchyKindOptions](#orghierarchykindoptions), or `custom` with the subtype in `customValue`. `description` is optional.
- `startDate` and `endDate` are optional `YYYY-MM-DD` dates.
- `status` is optional and is `active` or `inactive`. It describes the relationship, not either organization. It has no default and isn't derived from the dates, and the protocol requires no particular combination of dates and status.

An entry with only `org` is valid. Parents and children cover more than containment: a fiscal sponsor is a parent of kind `fiscalSponsor`, so not every parent owns or contains its child.

## OrgPatchData

A [JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396) body for updating an organization profile, used by the `PATCH /orgs/{orgId}` and `POST /orgs/{orgId}/changes` routes. It is derived from [OrganizationBase](#organizationbase): every field is optional, so a client sends only the fields it wants to change, clearable fields accept `null` to remove them, and read-only fields like `id` are excluded. Nested objects are themselves partial, so `{ "socials": { "website": null } }` clears just the website and leaves the other links untouched. Sent with a `Content-Type` of `application/merge-patch+json`.

From v0.5.0, `relationships` follows the same rules. Each relationship list is an array that a patch replaces whole, so `{ "relationships": { "parents": [...] } }` replaces only `parents` and leaves the other lists unchanged. `null` removes the addressed list, or every list when sent for `relationships`, and `[]` leaves a present, empty list. There is no append, merge by ID, single-entry change, or automatic reverse entry, so a writer changes one entry by sending its whole list with whole entries. In a patch, an entry's `org` has a writable `id` and an optional `name`, so it can name the other organization by `id` alone; validation doesn't fill in the `name` or `identifiers`. `dbaNames` is an array and is also replaced whole.
