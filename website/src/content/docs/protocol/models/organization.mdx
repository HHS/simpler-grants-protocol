## OrgRelationships

An organization's relationships to other organizations, added in v0.5.0 per [ADR 0030](https://github.com/HHS/simpler-grants-protocol/pull/1265) (draft). Every reference is stated on this organization and points to its target, using the existing [OrgRef](#orgref) shape. Containing organizations are grouped by kind under [`parents`](#orgparents). Fiscal sponsorship, succession, and duplicate identity are separate singular references, so an organization can be a department of one organization and fiscally sponsored by another at the same time. A relationship confers no authority over its target. See [Organization relationships](/guides/organization-relationships/) for worked examples.

| Property           | Meaning                                                                                                                            |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| parents            | Organizations that directly contain this one, grouped by hierarchy kind.                                                           |
| fiscalSponsor      | The target fiscally sponsors this organization or project. A payee designation alone is not sponsorship.                           |
| successor          | A different organization replaces this dissolved one. A rename or sponsor change alone is not succession.                          |
| duplicateOf        | This record duplicates the target, the canonical record of the same organization. Not a replacement organization.                  |
| otherRelationships | Additional nonhierarchical relationships under a documented label. Must not hold containment, sponsors, successors, or duplicates. |

When a field is absent the publisher did not provide it, an explicit `null` asserts it does not apply ([ADR 0024](https://commongrants.org/governance/adr/0024-optional-field-nullability/)), and an empty array is a present, empty collection. Whether a target exists, and whether the relationship graph is free of self-links, duplicate edges, and cycles, are checks the providing system performs; the schema validates shape only.

The schemas write `relationships`, `parents`, and the singular references as inline objects with the [OrgRelationships](#orgrelationships), [OrgParents](#orgparents), and [OrgRef](#orgref) shapes rather than as references, because OpenAPI 3.0 cannot mark a referenced object as nullable.

## OrgParents

Organizations that directly contain an organization, grouped by hierarchy kind and added in v0.5.0. Each kind holds an array, so several targets can share a kind; array order carries no primary-parent or ranking meaning. Use the most specific known kind, and don't repeat a target as both `parent` and a more specific kind. There is no separate division kind: `department` covers internal units.

| Kind         | Meaning                                                                                       |
| ------------ | --------------------------------------------------------------------------------------------- |
| parent       | Confirmed containment when no more specific supported kind is known.                          |
| department   | An internal organizational unit within the target.                                            |
| chapter      | A local or regional unit under the target's organizational structure, not merely a member.    |
| subsidiary   | A separate entity owned or controlled by the target.                                          |
| otherParents | Additional hierarchy kinds under a documented label that describes containment by the target. |

## OrgPatchData

A [JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396) body for updating an organization profile, used by the `PATCH /orgs/{orgId}` and `POST /orgs/{orgId}/changes` routes. It is derived from [OrganizationBase](#organizationbase): every field is optional, so a client sends only the fields it wants to change, clearable fields accept `null` to remove them, and read-only fields like `id` are excluded. Nested objects are themselves partial, so `{ "socials": { "website": null } }` clears just the website and leaves the other links untouched. Sent with a `Content-Type` of `application/merge-patch+json`.

From v0.5.0, `relationships` follows the same rules. Each hierarchy kind and each extension-map label is an array that a patch replaces whole, so `{ "relationships": { "parents": { "department": [{ "id": "…" }] } } }` replaces only the departments and leaves every other kind, label, and singular link unchanged. `null` removes the addressed kind, label, or link, and `[]` leaves a present empty collection. A relationship target in a patch is written with a writable `id`, and its `name` and `identifiers` are optional: the provider resolves the target by `id`, refreshes its name and identifiers, and rejects an unresolved target or contradictory metadata the sender supplied. A singular reference such as `fiscalSponsor` is an object, so a patch merges into it; changing only its `id` succeeds once the provider refreshes the metadata kept from the previous target. `dbaNames` is an array and is also replaced whole.
