## OrganizationBase

An organization that can apply to or host funding opportunities.

### Table

| Property      | Type                                                                                            | Required | Description                                                                         |
| ------------- | ----------------------------------------------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------- |
| id            | [uuid](/protocol/types/string#uuid)                                                             | Yes      | The organization's unique identifier.                                               |
| name          | [string](/protocol/types/string#string)                                                         | Yes      | The name this organization is known by; for a legal entity, its legal name.         |
| orgType       | [PCSOrgType](/protocol/fields/pcs#pcsorgtype)                                                   | No       | The organization's type within the Philanthropy Classification System (PCS).        |
| status        | [OrgStatus](#orgstatus)                                                                         | No       | Whether the organization exists and operates, or has dissolved or ceased operating. |
| identifiers   | [OrgIds](#orgids)                                                                               | No       | Identifiers associated with the organization, keyed by registry code.               |
| addresses     | [AddressCollection](/protocol/fields/address#addresscollection)                                 | No       | Collection of physical addresses associated with the organization.                  |
| phones        | [PhoneCollection](/protocol/fields/phone#phonecollection)                                       | No       | Collection of phone numbers associated with the organization.                       |
| emails        | [EmailCollection](/protocol/fields/email#emailcollection)                                       | No       | Collection of email addresses associated with the organization.                     |
| mission       | [string](/protocol/types/string#string)                                                         | No       | The organization's mission statement.                                               |
| yearFounded   | [calendarYear](/protocol/types/date#calendaryear)                                               | No       | The calendar year the organization was founded.                                     |
| socials       | [OrgSocialLinks](#orgsociallinks)                                                               | No       | The organization's social media and web presence links.                             |
| aliases       | [array](/protocol/types/other#array)\<[nonEmptyString](/protocol/types/string#nonemptystring)\> | No       | Other names this organization goes by, without repeats. Added in v0.5.0.            |
| relationships | [OrgRelationships](#orgrelationships)                                                           | No       | The organization's relationships to other organizations. Added in v0.5.0.           |
| customFields  | [Record](/protocol/types/other#record)\<[CustomField](/protocol/fields/custom-field)\>          | No       | Custom fields for the organization.                                                 |

`aliases` lists other names the same organization goes by, such as a trading name or a short form of its legal name, like "Agile Six" or "Agile6" for "Agile Six Applications, Inc.". It isn't a history of former names. Some systems instead keep a separate record for each trading name, which points at the legal entity with a `dba` entry in `parents` (see [OrgHierarchyKindOptions](#orghierarchykindoptions)). A name with its own trading-name record shouldn't also be listed in the legal entity's `aliases`, so readers don't count it twice; the schema doesn't check this. A trading-name record retired as a duplicate through `recordReplacedBy` isn't a live trading-name record, so its name can go in `aliases`.

## OrgRelationships

An organization's relationships to other organizations, added in v0.5.0 per [ADR 0030](https://commongrants.org/governance/adr/0030-org-relationships/). Each named list holds relationships of one category and direction, and `otherRelationships` holds connections outside those categories, which need not have a direction. Every list is optional, list order carries no meaning, and a provider can state a relationship from whichever organization's record it maintains. The protocol doesn't require reverse entries, complete lists, or agreement between the two sides. A relationship confers no authority over the other organization. See [Organization relationships](/guides/organization-relationships/) for worked examples.

| List               | Entry                                                   | Each entry says                                                     |
| ------------------ | ------------------------------------------------------- | ------------------------------------------------------------------- |
| parents            | [OrgHierarchyRelationship](#orghierarchyrelationship)   | `org` is above this organization                                    |
| children           | [OrgHierarchyRelationship](#orghierarchyrelationship)   | `org` is below this organization                                    |
| succeededBy        | [OrgSuccessionRelationship](#orgsuccessionrelationship) | `org` carries on all or part of this organization                   |
| succeeds           | [OrgSuccessionRelationship](#orgsuccessionrelationship) | This organization carries on all or part of `org`                   |
| recordReplacedBy   | [OrgRecordRelationship](#orgrecordrelationship)         | `org`'s record should be used instead of this record                |
| recordReplaces     | [OrgRecordRelationship](#orgrecordrelationship)         | This record should be used instead of `org`'s record                |
| otherRelationships | [OrgOtherRelationship](#orgotherrelationship)           | This organization is connected to `org`, possibly with no direction |

On reads, `relationships`, each list, `aliases`, and an entry's optional members are omitted when not provided; none accepts `null`. An empty array is a present, empty list. The schema validates shape only: it doesn't check whether the other organization exists or whether two records agree.

## OrgHierarchyRelationship

A parent or child relationship, added in v0.5.0. Every relationship list uses the same entry shape, defined once as a template; the entries differ only in the standard subtypes `kind` accepts.

- `org` is required and is an [OrgRef](#orgref). In a [patch](#orgpatchdata), `org.id` is writable and the rest is optional, so a writer can name the other organization by `id` alone. The receiver rejects an `id` it doesn't recognize, ignores a supplied `name` or `identifiers`, and fills both in from its own record on reads and revision snapshots. Validation doesn't look up or fill in the target.
- `kind` is optional. It is an [extensible enum](/protocol/fields/extensible-enum/) whose `value` is one of [OrgHierarchyKindOptions](#orghierarchykindoptions), or `custom` with the subtype in `customValue`. `description` is optional.
- `startDate` and `endDate` are optional `YYYY-MM-DD` dates.
- None of these members accepts `null`; an unstated member is omitted.
- `status` is optional and is one of [OrgRelationshipStatus](#orgrelationshipstatus). It describes the relationship, not either organization. It has no default and isn't derived from the dates, and the protocol requires no particular combination of dates and status.

An entry with only `org` is valid. Parents and children cover more than containment: a fiscal sponsor is a parent of kind `fiscalSponsor`, so not every parent owns or contains its child.

## OrgHierarchyKindOptions

The standard subtypes of a parent or child relationship, added in v0.5.0. `dba` is for systems that keep a separate record per trading name: in `parents`, it means this record is a name the referenced legal entity does business under, and in `children`, that the referenced record is a trading-name record of this one. Most systems list trading names in the legal entity's `aliases` instead, and a name with its own `dba` record shouldn't be listed in both. `department` names an internal unit; it isn't defined to cover every internal level, such as a division or agency, which a provider can name with a custom kind. There is no generic `parent` value: an entry without `kind` already states a parent or child relationship.

## OrgPatchData

A [JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396) body for updating an organization profile, used by the `PATCH /orgs/{orgId}` and `POST /orgs/{orgId}/changes` routes. It is derived from [OrganizationBase](#organizationbase): every field is optional, so a client sends only the fields it wants to change, clearable fields accept `null` to remove them, and read-only fields like `id` are excluded. Nested objects are themselves partial, so `{ "socials": { "website": null } }` clears just the website and leaves the other links untouched. Sent with a `Content-Type` of `application/merge-patch+json`.

From v0.5.0, `relationships` follows the same rules. Each relationship list is an array that a patch replaces whole, so `{ "relationships": { "parents": [...] } }` replaces only `parents` and leaves the other lists unchanged. `null` removes the addressed list, or every list when sent for `relationships`, and `[]` leaves a present, empty list. There is no append, merge by ID, single-entry change, or automatic reverse entry, so a writer changes one entry by sending its whole list with whole entries. In a patch, an entry's `org` has a writable `id` and an optional `name` and `identifiers`, so it can name the other organization by `id` alone. The receiver rejects an `id` it doesn't recognize, ignores a supplied `name` or `identifiers`, and fills both in from its own record on reads and revision snapshots, so a writer can also resend entries copied from a read. Validation doesn't look up or fill in the target. `aliases` is an array and is also replaced whole, and `null` removes it. Apart from the target's `name` and `identifiers`, a replaced list's entries are stored as written, so an entry's optional `kind`, dates, and `status` are omitted rather than set to `null`.
