Learn how to implement a CommonGrants API in TypeScript using the [Hono API template](https://github.com/common-grants/cg-api-template-hono) and the [CommonGrants TypeScript SDK](https://github.com/HHS/simpler-grants-protocol/tree/main/lib/ts-sdk#readme).

## Quickstart

This guide walks you through creating a new project from the CommonGrants Hono template, then using the SDK to validate your data and define custom fields.

:::note[Prerequisites]

- [Node.js](https://nodejs.org/) v24 (check with `node --version`). The template supports Node.js 24 only and includes an `.nvmrc` file.
- [pnpm](https://pnpm.io/installation) v11 or later (check with `pnpm --version`). The template's scripts use pnpm.
- Port `3000` free for the development server.

:::

### First steps

Get the Hono template up and running with the following steps:

<Steps>
1. Open the [template repository](https://github.com/common-grants/cg-api-template-hono) and click **Use this template** to create your own repository from it.

2. Clone your new repository:

   ```bash
   git clone https://github.com/<you>/<your-api>.git
   cd <your-api>
   ```

3. Install the dependencies:

   ```bash
   pnpm install
   ```

4. Run the project:

   ```bash
   pnpm run dev
   ```

5. Open the API docs at `http://localhost:3000/docs`. Press `Ctrl+C` in the terminal to stop the server when you're done.

</Steps>

### Project structure

The template includes the following files and directories:

<FileTree>

- src/
  - index.ts Node entrypoint — the only file that knows about Node
  - app.ts `createApp({ repository })` builds the app
  - http.ts Shared error shapes
  - routes/
    - opportunities.ts Route definitions, handlers, request/response validation
  - data/
    - schema.ts The one opportunity schema — extend custom fields here
    - repository.ts The interface your data source implements: list / get / search
    - fixtures.ts The sample-data implementation of that interface
    - opportunities.json The bundled sample data
- test/ Vitest suites: fixtures, app, routes, OpenAPI

</FileTree>

## Next steps

Once the template is running, connect the API to your data. If your project started from an earlier version of the template, upgrade its SDK first.

### Upgrading from an earlier SDK

The [`@common-grants/sdk`](https://www.npmjs.com/package/@common-grants/sdk) package provides Zod schemas, TypeScript types, and an extension framework that match the current protocol version. The template depends on SDK 0.9. If your project uses an earlier version, upgrade it and run the checks:

```bash
pnpm add @common-grants/sdk@^0.9.0
pnpm run ci
```

SDK 0.9 updates the schemas to protocol v0.5 and is published as ESM only. The template is already an ES module project, so it needs no configuration changes.

The SDK is split into modules, each with its own import path:

| Import path                     | Description                                   |
| ------------------------------- | --------------------------------------------- |
| `@common-grants/sdk/schemas`    | Zod schemas for data validation               |
| `@common-grants/sdk/types`      | Inferred TypeScript types                     |
| `@common-grants/sdk/constants`  | Runtime enum constants                        |
| `@common-grants/sdk/extensions` | Custom field and plugin framework             |
| `@common-grants/sdk/client`     | HTTP client with auth, pagination, and search |

The SDK exposes these modules through `package.json` `exports` and has no root entrypoint, so import from the paths above.

### Validate data with the SDK

The template and the SDK split the work. The template owns HTTP: routing, request and response validation, error bodies, the OpenAPI document, and the API docs at `/docs`. The SDK owns the CommonGrants schemas: the template builds its opportunity model, filters, and response envelopes from them, so when you update the SDK, your API picks up that release's schema changes.

Use the same schemas to validate records from your data source:

```typescript
import { OpportunityBaseSchema } from "@common-grants/sdk/schemas";
import type { OpportunityBase } from "@common-grants/sdk/types";

// rawData is a record from your data source
// Throws a ZodError if it doesn't match the protocol
const opportunity: OpportunityBase = OpportunityBaseSchema.parse(rawData);
```

### Connect your own data

The template reads the bundled sample data through the `OpportunityRepository` interface in `src/data/repository.ts`. The interface has three methods, `list`, `get`, and `search`, behind these routes:

- `GET /common-grants/opportunities`
- `GET /common-grants/opportunities/{oppId}`
- `POST /common-grants/opportunities/search`

To serve your own data:

1. Implement `OpportunityRepository` against your database or upstream API, in place of the sample-data implementation, `fixtureRepository` in `src/data/fixtures.ts`. Parse each record with an SDK schema, or map it with a plugin's `toCommon`.
2. Pass your implementation to `createApp` in `src/index.ts`.

The routes, validation, and OpenAPI document keep working without changes. The template's [porting guide](https://github.com/common-grants/cg-api-template-hono/blob/main/PORTING.md) walks through these steps.

### Adding custom fields

When adopting the CommonGrants protocol, you may need to include information about a funding opportunity that is not explicitly defined by the CommonGrants model for opportunities. The protocol supports this through the `customFields` property on the `OpportunityBase` model, and the SDK's extensions module gives those fields types.

For example, let's say you need to add a `legacyId` field to map opportunities to an existing ID system.

#### Define a plugin

Create a plugin that declares the custom field. The plugin compiles an `Opportunity` schema with a typed `customFields` property:

```typescript title=src/data/plugin.ts
import { z } from "zod";
import { definePlugin } from "@common-grants/sdk/extensions";

/** Custom fields for this API's data source */
export const myPlugin = definePlugin({
  meta: {
    name: "my-system",
    sourceSystem: "grants.example.gov",
    capabilities: ["customFields"],
  },
  schemas: {
    Opportunity: {
      customFields: {
        legacyId: {
          fieldType: "integer",
          description: "Maps to the opportunity_id in the legacy system",
        },
      },
    },
  },
} as const);

/** Opportunity schema with typed custom fields */
export const OpportunitySchema = myPlugin.schemas.Opportunity.commonSchema;
export type Opportunity = z.infer<typeof OpportunitySchema>;
```

The `as const` is only required when the specs are assigned to a variable before the call, but the SDK keeps it by convention.

#### Use the plugin's schema

Parse your data with the plugin's schema instead of the base schema, for example in a new file under `src/`. The custom field is validated and fully typed:

```typescript
import { OpportunitySchema, type Opportunity } from "./data/plugin.js";

const opportunity: Opportunity = OpportunitySchema.parse({
  id: "573525f2-8e15-4405-83fb-e6523511d893",
  title: "STEM Education Grant Program",
  description: "Improving STEM education in underserved communities",
  status: { value: "open" },
  createdAt: "2025-01-01T00:00:00Z",
  lastModifiedAt: "2025-01-15T00:00:00Z",
  customFields: {
    legacyId: { name: "legacyId", fieldType: "integer", value: 12345 },
  },
});

opportunity.customFields?.legacyId?.value; // number
```

To serve the custom field from the API, set `OpportunitySchema` in `src/data/schema.ts` to the plugin's schema. Response validation, the repository's types, and the OpenAPI document all pick it up. A plugin's custom filters don't come with it: the template's search route ignores them and reports them in `filterInfo.errors`. To support them, update the search route and your repository.

For a one-off extension without a plugin, use `withCustomFields()` from the same module. See the [extensions guide](https://github.com/HHS/simpler-grants-protocol/blob/main/lib/ts-sdk/src/extensions/README.md) for custom filters, transforms, and publishing plugins.
