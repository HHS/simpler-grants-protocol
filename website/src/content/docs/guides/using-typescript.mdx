The [Hono API template](https://github.com/common-grants/cg-api-template-hono) is a working CommonGrants API. You run it first, then connect it to your own data. It serves the opportunity endpoints from bundled sample data. It validates every request and response with the schemas from the published [`@common-grants/sdk`](https://www.npmjs.com/package/@common-grants/sdk) package. It also generates an OpenAPI 3.1 document from those same schemas and serves Swagger UI so you can browse it. The template is built with [Hono](https://hono.dev) and [`@hono/zod-openapi`](https://github.com/honojs/middleware/tree/main/packages/zod-openapi).

## Prerequisites

- **Node.js 24.** The template includes an `.nvmrc` file for `nvm` users.
- **[pnpm](https://pnpm.io) 11.20.0.** The template pins this version in the `packageManager` field of `package.json`.

The template needs no other global packages, credentials, database, or infrastructure.

## Get started

<Steps>

1. Open the [template repository](https://github.com/common-grants/cg-api-template-hono) and click **Use this template** to create your own repository from it.

2. Clone your new repository:

   ```bash
   git clone https://github.com/<you>/<your-api>.git
   cd <your-api>
   ```

3. Check your versions:

   ```bash
   node --version # must report v24.x
   pnpm --version # must report 11.20.0
   ```

4. Install the dependencies from the lockfile:

   ```bash
   pnpm install --frozen-lockfile
   ```

5. Check that everything works before you change anything:

   ```bash
   pnpm run ci
   ```

   This runs the lint, format, and type checks, the build, and the test suite with coverage. The template's hosted CI runs the same command, then `pnpm run audit`.

6. Start the server:

   ```bash
   pnpm run dev
   ```

   The server listens on port 3000 and reloads when you change a file.

7. Open [http://localhost:3000/docs](http://localhost:3000/docs) to browse the API in Swagger UI and try a request from the browser. Swagger UI loads its assets from the jsDelivr CDN.

8. In another terminal, send a few requests:

   ```bash
   # A page of opportunities, most recently modified first
   curl 'http://localhost:3000/common-grants/opportunities?pageSize=2'

   # Filtered and sorted search
   curl -X POST http://localhost:3000/common-grants/opportunities/search \
     -H 'Content-Type: application/json' \
     -d '{"filters":{"status":{"operator":"in","value":["open"]}},"sorting":{"sortBy":"title"}}'

   # The OpenAPI 3.1 document, generated from the same schemas
   curl http://localhost:3000/openapi.json
   ```

   Both responses use the protocol's standard response envelopes. A list response contains `items` and `paginationInfo`. A search response also contains `sortInfo` and `filterInfo`.

</Steps>

## Project structure

<FileTree>

- src/
  - index.ts Node entrypoint — the only file that knows about Node
  - app.ts `createApp({ repository })` — runtime-neutral factory
  - http.ts Shared error shapes
  - routes/
    - opportunities.ts Route definitions, handlers, request/response validation
  - data/
    - schema.ts The one opportunity schema — extend custom fields here
    - repository.ts The data seam: list / get / search
    - fixtures.ts Reference implementation over the bundled sample data
    - opportunities.json The bundled sample data
- test/ Vitest suites: fixtures, app, routes, OpenAPI

</FileTree>

## How the pieces fit

The template and the SDK split the work. The template owns HTTP: routing, request and response validation, error bodies, the OpenAPI document, and Swagger UI. The SDK owns the CommonGrants schemas.

The template imports these schemas from `@common-grants/sdk/schemas` instead of defining its own:

- the opportunity model
- the filter, sorting, and pagination schemas
- the response envelopes

When you update the SDK, your API picks up the protocol changes in that release.

To add fields that the core opportunity model doesn't define, use `withCustomFields` in `src/data/schema.ts`. This file is the one place to add custom fields. It defines the opportunity model for the whole API, so response validation, the repository's types, and the OpenAPI document all pick up your new fields:

```typescript title="src/data/schema.ts"
import { OpportunityBaseSchema } from "@common-grants/sdk/schemas";
import { withCustomFields } from "@common-grants/sdk/extensions";
import { z } from "zod";

const LegacyIdValueSchema = z.object({
  system: z.string(),
  id: z.number().int(),
});

export const OpportunitySchema = withCustomFields(OpportunityBaseSchema, {
  legacyId: {
    fieldType: "object",
    value: LegacyIdValueSchema,
    description: "Maps to the opportunity_id in the legacy system",
  },
  category: {
    fieldType: "string",
    description: "Grant category",
  },
} as const);

export type Opportunity = z.output<typeof OpportunitySchema>;
```

`withCustomFields` extends a schema inside one codebase. To reuse the same extensions in other code, package them as a plugin with `definePlugin`. That other code might be a client that consumes your API, or another service that reads from the same source system.

A plugin can bundle three things:

- custom fields
- custom filters
- transforms between your source system's data and CommonGrants

You can use a plugin's `schemas.Opportunity.commonSchema` as the opportunity schema in `src/data/schema.ts`. This brings in the plugin's custom fields only. The template's search route doesn't apply custom filters. It ignores them and lists them in `filterInfo.errors`. To support a plugin's custom filters, update the search route and your repository.

See [extensions in the TypeScript SDK](https://github.com/HHS/simpler-grants-protocol/blob/main/lib/ts-sdk/src/extensions/README.md) for both approaches. The [custom fields overview](/custom-fields/overview/) explains how custom fields work across the protocol. The [plugin catalog](/plugins/) lists existing plugins.

## Connect your own data

The template reads the bundled sample data through the `OpportunityRepository` interface in `src/data/repository.ts`. The interface has three methods: `list`, `get`, and `search`.

To serve your own data:

1. Implement `OpportunityRepository` against your database or upstream API.
2. Pass your implementation to `createApp` in `src/index.ts`.

The routes, validation, and OpenAPI document keep working without changes.

The template's [porting guide](https://github.com/common-grants/cg-api-template-hono/blob/main/PORTING.md) walks through these steps. It covers stable UUIDs for your records, dates and money in filters and sorts, which tests to keep, and what to change before you ship.
