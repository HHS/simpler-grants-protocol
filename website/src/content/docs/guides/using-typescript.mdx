The [Hono API template](https://github.com/common-grants/cg-api-template-hono) is a working CommonGrants API that you run first and then point at your own data. It serves the opportunity endpoints from bundled sample data, validates every request and response with the published [`@common-grants/sdk`](https://www.npmjs.com/package/@common-grants/sdk) schemas, generates an OpenAPI 3.1 document from those same schemas, and serves Swagger UI to browse it. It's built with [Hono](https://hono.dev) and [`@hono/zod-openapi`](https://github.com/honojs/middleware/tree/main/packages/zod-openapi).

## Prerequisites

- **Node.js 24.** The template includes an `.nvmrc` file for `nvm` users.
- **[pnpm](https://pnpm.io) 11.20.0.** The template pins this version in the `packageManager` field of `package.json`.

The template needs no other global packages, credentials, database, or infrastructure.

## Get started

<Steps>

1. Open the [template repository](https://github.com/common-grants/cg-api-template-hono) and click **Use this template** to create your own repository from it.

2. Clone your new repository:

   ```bash
   git clone https://github.com/<you>/<your-api>.git
   cd <your-api>
   ```

3. Check your versions:

   ```bash
   node --version # must report v24.x
   pnpm --version # must report 11.20.0
   ```

4. Install the dependencies from the lockfile:

   ```bash
   pnpm install --frozen-lockfile
   ```

5. Check that everything works before you change anything:

   ```bash
   pnpm run ci
   ```

   This runs the lint, format, and type checks, the build, and the test suite with coverage. The template's hosted CI runs the same command, then `pnpm run audit`.

6. Start the server:

   ```bash
   pnpm run dev
   ```

   The server listens on port 3000 and reloads when you change a file.

7. Open [http://localhost:3000/docs](http://localhost:3000/docs) to browse the API in Swagger UI and try a request from the browser. Swagger UI loads its assets from the jsDelivr CDN.

8. In another terminal, send a few requests:

   ```bash
   # A page of opportunities, most recently modified first
   curl 'http://localhost:3000/common-grants/opportunities?pageSize=2'

   # Filtered and sorted search
   curl -X POST http://localhost:3000/common-grants/opportunities/search \
     -H 'Content-Type: application/json' \
     -d '{"filters":{"status":{"operator":"in","value":["open"]}},"sorting":{"sortBy":"title"}}'

   # The OpenAPI 3.1 document, generated from the same schemas
   curl http://localhost:3000/openapi.json
   ```

   The list and search responses use the protocol's response envelopes: `items` and `paginationInfo`, plus `sortInfo` and `filterInfo` for search.

</Steps>

## Project structure

<FileTree>

- src/
  - index.ts Node entrypoint — the only file that knows about Node
  - app.ts `createApp({ repository })` — runtime-neutral factory
  - http.ts Shared error shapes
  - routes/
    - opportunities.ts Route definitions, handlers, request/response validation
  - data/
    - schema.ts The one opportunity schema — extend custom fields here
    - repository.ts The data seam: list / get / search
    - fixtures.ts Reference implementation over the bundled sample data
    - opportunities.json The bundled sample data
- test/ Vitest suites: fixtures, app, routes, OpenAPI

</FileTree>

## How the pieces fit

The template owns HTTP: routing, request and response validation, error bodies, the OpenAPI document, and Swagger UI. The SDK owns the CommonGrants schemas. The opportunity model, the filter, sorting, and pagination schemas, and the response envelopes are imported from `@common-grants/sdk/schemas` rather than redefined, so an SDK update brings protocol changes into your API.

To carry data the core model doesn't define, extend the opportunity schema with `withCustomFields` in `src/data/schema.ts`. That file is the single definition of the opportunity model, so the response validation, the repository's types, and the OpenAPI document all pick up the change:

```typescript title="src/data/schema.ts"
import { OpportunityBaseSchema } from "@common-grants/sdk/schemas";
import { withCustomFields } from "@common-grants/sdk/extensions";
import { z } from "zod";

const LegacyIdValueSchema = z.object({
  system: z.string(),
  id: z.number().int(),
});

export const OpportunitySchema = withCustomFields(OpportunityBaseSchema, {
  legacyId: {
    fieldType: "object",
    value: LegacyIdValueSchema,
    description: "Maps to the opportunity_id in the legacy system",
  },
  category: {
    fieldType: "string",
    description: "Grant category",
  },
} as const);

export type Opportunity = z.output<typeof OpportunitySchema>;
```

`withCustomFields` extends a schema inside one codebase. When other code needs the same extensions, such as the clients that consume your API or another service that reads the same source system, package them as a plugin with `definePlugin`. A plugin bundles custom fields, custom filters, and transforms between your source system's data and CommonGrants, and its `schemas.Opportunity.commonSchema` can serve as the opportunity schema in `src/data/schema.ts`. See [extensions in the TypeScript SDK](https://github.com/HHS/simpler-grants-protocol/blob/main/lib/ts-sdk/src/extensions/README.md) for both approaches, the [custom fields overview](/custom-fields/overview/) for how custom fields work across the protocol, and the [plugin catalog](/plugins/) for existing plugins.

## Connect your own data

The bundled sample data sits behind the `OpportunityRepository` interface in `src/data/repository.ts`, which has three methods: `list`, `get`, and `search`. Implement that interface against your database or upstream API, pass your implementation to `createApp` in `src/index.ts`, and the routes, validation, and OpenAPI document keep working unchanged. The template's [porting guide](https://github.com/common-grants/cg-api-template-hono/blob/main/PORTING.md) walks through it, including stable UUIDs for your records, dates and money in filters and sorts, which tests to keep, and what to change before you ship.
