Learn how to implement a CommonGrants API in TypeScript using the [Express.js](https://expressjs.com/) web framework and the [CommonGrants TypeScript SDK](https://github.com/HHS/simpler-grants-protocol/tree/main/lib/ts-sdk#readme).

## Quickstart

This guide walks you through setting up a new project from the CommonGrants Express.js template, then adding the SDK to validate your data and define custom fields.

:::note[Prerequisites]

- [Node.js](https://nodejs.org/) v22 or later (check with `node --version`). The SDK is published as ESM and requires Node.js 22+.
- [pnpm](https://pnpm.io/installation) v11 or later (check with `pnpm --version`). The template's scripts use pnpm.
- Port `3000` free for the development server.

:::

### First steps

Get an Express.js project up and running with the following steps:

<Steps>
1. Create a new directory for your project:

    ```bash
    mkdir common-grants-api
    cd common-grants-api
    ```

2. Set up your project using the CommonGrants CLI:

   ```bash
   npx @common-grants/cli@0.4.1 init --template express-js
   ```

   `npx` ships with Node.js. Bun users can run `bunx` instead. `pnpm dlx` can't run `cg init` yet.

3. Create `pnpm-workspace.yaml` so pnpm skips the optional install scripts in the template's dependencies:

   ```yaml title=pnpm-workspace.yaml
   allowBuilds:
     "@scarf/scarf": false
     esbuild: false
   ```

   Without this file, pnpm stops every `pnpm run` command with an "Ignored build scripts" error.

4. Install the dependencies:

   ```bash
   pnpm install
   ```

5. Run the project:

   ```bash
   pnpm run dev
   ```

6. Open the API docs at `http://localhost:3000/docs`. Press `Ctrl+C` in the terminal to stop the server when you're done.

</Steps>

### Project structure

The template includes the following files and directories:

<FileTree>

- package.json # Node.js project configuration and dependencies
- pnpm-lock.yaml # Locked versions of dependencies
- pnpm-workspace.yaml # pnpm settings (created in step 3)
- tsconfig.json # TypeScript configuration
- tspconfig.yaml # TypeSpec emitter configuration
- eslint.config.js # ESLint configuration
- .prettierrc # Prettier configuration
- README.md # Project documentation
- src/
  - api/
    - index.ts # Express application setup and config
    - controllers/ # Request handlers and routers
    - errors/ # API error types
    - middleware/ # Error handling and validation middleware
    - schemas/ # Zod schemas for (de)serialization
    - services/ # Business logic and data operations
  - typespec/
    - main.tsp # The TypeSpec specification for your API

</FileTree>

## Next steps

Once the template is running, add the SDK and connect the API to your data.

### Add the SDK

The [`@common-grants/sdk`](https://www.npmjs.com/package/@common-grants/sdk) package provides Zod schemas, TypeScript types, and an extension framework that match the current protocol version. Install it and the matching TypeSpec library:

```bash
pnpm add --save-exact @common-grants/sdk@0.9.0 @common-grants/core@0.5.0
pnpm add --save-exact -D @typespec/compiler@1.17.0 @typespec/http@1.17.0 @typespec/openapi@1.17.0 @typespec/openapi3@1.17.0 @typespec/json-schema@1.17.0 @typespec/rest@0.87.0 @typespec/versioning@0.87.0
```

The SDK exposes its modules through `package.json` `exports`, which the template's `"moduleResolution": "node"` setting ignores. In `tsconfig.json`, replace `"module": "CommonJS"` and `"moduleResolution": "node"` with:

```json title=tsconfig.json
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
```

Then point the template's TypeSpec spec at protocol v0.5 so the API docs at `/docs` match the SDK's schemas. In `src/typespec/main.tsp`, change `v0_2` to `v0_5`:

```tsp title=src/typespec/main.tsp
@Versioning.useDependency(CommonGrants.Versions.v0_5)
```

Confirm everything still type-checks and runs:

```bash
pnpm exec tsc --noEmit
pnpm run dev
```

The docs now describe v0.5 models, but the API's responses still follow the template's own schemas until you swap in the SDK's, as described next.

The SDK is split into modules, each with its own import path:

| Import path                     | Description                                   |
| ------------------------------- | --------------------------------------------- |
| `@common-grants/sdk/schemas`    | Zod schemas for data validation               |
| `@common-grants/sdk/types`      | Inferred TypeScript types                     |
| `@common-grants/sdk/constants`  | Runtime enum constants                        |
| `@common-grants/sdk/extensions` | Custom field and plugin framework             |
| `@common-grants/sdk/client`     | HTTP client with auth, pagination, and search |

### Validate data with the SDK

The template ships its own Zod schemas in `src/api/schemas/`. The SDK provides maintained equivalents for every protocol model, filter, and response, so you can replace the template's schemas as you build:

```typescript
import { OpportunityBaseSchema } from "@common-grants/sdk/schemas";
import type { OpportunityBase } from "@common-grants/sdk/types";

// rawData is a record from your data source
// Throws a ZodError if it doesn't match the protocol
const opportunity: OpportunityBase = OpportunityBaseSchema.parse(rawData);
```

### Implementing services

The services layer in `src/api/services/` holds the business logic and data operations for the API. Focus on `opportunity.service.ts`, which implements the `OpportunitiesService` class behind these routes:

- `GET /common-grants/opportunities`
- `GET /common-grants/opportunities/{oppId}`
- `POST /common-grants/opportunities/search`

Specific changes to make in this file:

- Replace the mock data with a real data source, e.g. a database query or a remote API call, and parse each record with an SDK schema.
- Look opportunities up by `id` instead of title in `OpportunitiesService.getOpportunityByTitle`.
- Add the sorting and filtering logic to the `OpportunitiesService.searchOpportunities` method.

### Adding custom fields

When adopting the CommonGrants protocol, you may need to include information about a funding opportunity that is not explicitly defined by the CommonGrants model for opportunities. The protocol supports this through the `customFields` property on the `OpportunityBase` model, and the SDK's extensions module gives those fields types.

For example, let's say you need to add a `legacyId` field to map opportunities to an existing ID system.

#### Define a plugin

Create a plugin that declares the custom field. The plugin compiles an `Opportunity` schema with a typed `customFields` property:

```typescript title=src/api/schemas/plugin.ts
import { z } from "zod";
import { definePlugin } from "@common-grants/sdk/extensions";

/** Custom fields for this API's data source */
export const myPlugin = definePlugin({
  meta: {
    name: "my-system",
    sourceSystem: "grants.example.gov",
    capabilities: ["customFields"],
  },
  schemas: {
    Opportunity: {
      customFields: {
        legacyId: {
          fieldType: "integer",
          description: "Maps to the opportunity_id in the legacy system",
        },
      },
    },
  },
} as const);

/** Opportunity schema with typed custom fields */
export const OpportunitySchema = myPlugin.schemas.Opportunity.commonSchema;
export type Opportunity = z.infer<typeof OpportunitySchema>;
```

The `as const` is only required when the specs are assigned to a variable before the call, but the SDK keeps it by convention.

#### Use the plugin's schema

Parse your data with the plugin's schema instead of the base schema. The custom field is validated and fully typed:

```typescript
import { OpportunitySchema, type Opportunity } from "./schemas/plugin";

const opportunity: Opportunity = OpportunitySchema.parse({
  id: "573525f2-8e15-4405-83fb-e6523511d893",
  title: "STEM Education Grant Program",
  description: "Improving STEM education in underserved communities",
  status: { value: "open" },
  createdAt: "2025-01-01T00:00:00Z",
  lastModifiedAt: "2025-01-15T00:00:00Z",
  customFields: {
    legacyId: { name: "legacyId", fieldType: "integer", value: 12345 },
  },
});

opportunity.customFields?.legacyId?.value; // number
```

The template's services still import their own `Opportunity` type from `src/api/schemas`. Replace those imports with the plugin's schema and type as you wire in real data, so the two don't collide.

For a one-off extension without a plugin, use `withCustomFields()` from the same module. See the [extensions guide](https://github.com/HHS/simpler-grants-protocol/blob/main/lib/ts-sdk/src/extensions/README.md) for custom filters, transforms, and publishing plugins.
