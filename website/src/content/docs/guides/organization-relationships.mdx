:::caution[Draft for review]
This page shows the organization relationships proposed in [ADR 0030](https://github.com/HHS/simpler-grants-protocol/pull/1265), which is still under review. The fields are part of protocol v0.5.0, which has not been released, and may change before it is. Every organization, name, and ID on this page is illustrative, not a real record or a classification of a real organization.

The examples are static documentation, checked against the draft schemas. The mock API behind "Try it out" in the [API reference](/protocol/api-docs) only validates a write and echoes the result. It doesn't resolve targets, check sender metadata, or check the relationship graph, so an ID-only relationship write can return a snapshot that isn't a valid organization read.
:::

An organization can point to other organizations it is related to: the organization that contains it, the one that fiscally sponsors it, the one that replaced it, or the canonical record it duplicates. Each kind of relationship means something different, so each has its own place in [`relationships`](/protocol/models/organization#orgrelationships). Names the organization trades under go in `dbaNames`, not in a relationship.

| You want to say                                        | Use                                                          |
| ------------------------------------------------------ | ------------------------------------------------------------ |
| This organization is part of another one               | `relationships.parents`, under the most specific known kind  |
| Another organization fiscally sponsors this one        | `relationships.fiscalSponsor`                                |
| A different organization replaced this dissolved one   | `relationships.successor`                                    |
| This record is a duplicate of another record           | `relationships.duplicateOf`                                  |
| Some other documented, nonhierarchical relationship    | `relationships.otherRelationships`, under a documented label |
| The organization does business under other names today | `dbaNames`                                                   |

Every relationship is stated on the organization it describes and points to its target, using the existing [`OrgRef`](/protocol/models/organization#orgref) shape: the target's `id`, `name`, and, optionally, `identifiers` that let another system match it. A relationship gives no authority over its target.

## Containment

Hierarchy kinds sit under `relationships.parents`. Each kind holds an array, and each record names only the organization that _directly_ contains it.

| Kind           | Meaning                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------ |
| `parent`       | Confirmed containment when no more specific kind is known.                                 |
| `department`   | An internal unit within the target. This also covers divisions.                            |
| `chapter`      | A local or regional unit under the target's organizational structure, not merely a member. |
| `subsidiary`   | A separate entity owned or controlled by the target.                                       |
| `otherParents` | Another kind of containment, under a label the publisher documents.                        |

### A chain of immediate parents

An agency, a sub-agency within it, and an office within that each name only their immediate container. A consumer that wants the full chain follows each reference to the next record. When only containment is known, use `parent` rather than guessing a more specific kind.

```json title="Organization: an office naming its immediate parent"
{
  "id": "1d2e3f40-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
  "name": "Example Office of Grant Programs",
  "relationships": {
    "parents": {
      "parent": [
        {
          "id": "2e3f4051-6b7c-4d8e-9f0a-1b2c3d4e5f60",
          "name": "Example Institute of Food and Agriculture"
        }
      ]
    }
  }
}
```

```json title="Organization: the sub-agency naming its own parent"
{
  "id": "2e3f4051-6b7c-4d8e-9f0a-1b2c3d4e5f60",
  "name": "Example Institute of Food and Agriculture",
  "relationships": {
    "parents": {
      "parent": [
        {
          "id": "3f405162-7c8d-4e9f-8a1b-2c3d4e5f6071",
          "name": "Example Department of Agriculture"
        }
      ]
    }
  }
}
```

### A chapter compared with a network member

A chapter sits inside the target's organizational structure. An independent organization that belongs to a national network is not a chapter and has no parent; if the publisher wants to record the membership, it can use a documented nonhierarchical label instead.

```json title="Organization: a chapter of a national federation"
{
  "id": "40516273-8d9e-4f0a-9b2c-3d4e5f607182",
  "name": "Example Homebuilders of Riverside County",
  "relationships": {
    "parents": {
      "chapter": [
        {
          "id": "51627384-9e0f-4a1b-8c3d-4e5f60718293",
          "name": "Example Homebuilders International"
        }
      ]
    }
  }
}
```

```json title="Organization: an independent network member with no parent"
{
  "id": "62738495-0f1a-4b2c-9d4e-5f60718293a4",
  "name": "Example Neighborhood Fund",
  "relationships": {
    "parents": null,
    "otherRelationships": {
      "networkMember": [
        {
          "id": "738495a6-1a2b-4c3d-8e5f-60718293a4b5",
          "name": "Example National Giving Network"
        }
      ]
    }
  }
}
```

Here `"parents": null` asserts that hierarchy does not apply. Leaving `parents` out would instead mean the publisher did not say. `networkMember` is an illustrative label: a publisher that uses a custom label documents what it means.

### Several parents of one kind

An array can hold several targets of the same kind, such as a center run jointly as a department of two institutions. Array order means nothing: the first entry is not a primary parent. This is allowed so that a later need doesn't require changing the field from one reference to a list; no adopter has needed it yet.

```json title="Organization: a joint center with two containing institutions"
{
  "id": "8495a6b7-2b3c-4d4e-9f60-718293a4b5c6",
  "name": "Example Joint Center for Rural Health",
  "relationships": {
    "parents": {
      "department": [
        {
          "id": "95a6b7c8-3c4d-4e5f-8071-8293a4b5c6d7",
          "name": "Example State University"
        },
        {
          "id": "a6b7c8d9-4d5e-4f60-9182-93a4b5c6d7e8",
          "name": "Example Medical College"
        }
      ]
    }
  }
}
```

## Fiscal sponsorship alongside containment

Sponsorship is not containment, so it is recorded separately and can sit alongside a parent. A payee designation alone does not establish sponsorship.

```json title="Organization: a department with a different fiscal sponsor"
{
  "id": "b7c8d9e0-5e6f-4a71-8293-a4b5c6d7e8f9",
  "name": "Example Community Garden Project",
  "relationships": {
    "parents": {
      "department": [
        {
          "id": "c8d9e0f1-6f70-4b82-93a4-b5c6d7e8f90a",
          "name": "Example Parks Conservancy",
          "identifiers": {
            "org:us:ein": {
              "registry": { "code": "org:us:ein" },
              "id": "123456789"
            }
          }
        }
      ]
    },
    "fiscalSponsor": {
      "id": "d9e0f102-7081-4c93-a4b5-c6d7e8f90a1b",
      "name": "Example Community Foundation"
    }
  }
}
```

The `identifiers` on a reference let another system match the target without knowing this system's IDs.

## Duplicates and successors

A duplicate and a successor answer different questions. `duplicateOf` says two records describe the _same_ organization and points to the canonical one. `successor` says a _different_ organization replaced one that dissolved; both records describe real organizations.

```json title="Organization: a duplicate record pointing to the canonical record"
{
  "id": "e0f10213-8192-4da4-b5c6-d7e8f90a1b2c",
  "name": "Example Health Clinic",
  "relationships": {
    "duplicateOf": {
      "id": "f1021324-92a3-4eb5-86d7-e8f90a1b2c3d",
      "name": "Example Health Clinic"
    }
  }
}
```

```json title="Organization: a dissolved organization pointing to its successor"
{
  "id": "02132435-a3b4-4fc6-97e8-f90a1b2c3d4e",
  "name": "Example Literacy Coalition",
  "relationships": {
    "successor": {
      "id": "13243546-b4c5-4ad7-88f9-0a1b2c3d4e5f",
      "name": "Example Reading Partners"
    }
  }
}
```

The duplicate record is kept, with its link, so an old reference can still find the canonical record. The protocol doesn't require redirects, hiding duplicates from lists, or deleting them. A rename is not succession: a renamed organization keeps its record and changes its `name`.

## DBA names

Names an organization currently does business as are plain strings on the organization itself. They are not separate organizations, and they are not a history of former names.

```json title="Organization: one organization trading under two names"
{
  "id": "24354657-c5d6-4be8-99a0-1b2c3d4e5f60",
  "name": "Example Riverside Arts Alliance, Inc.",
  "dbaNames": ["Riverside Arts", "The Gallery on Main"]
}
```

## Updating relationships

Relationships are updated with the same [JSON Merge Patch](/protocol/models/organization#orgpatchdata) as the rest of the organization profile. Each hierarchy kind and each custom label is an array, and a patch replaces only the array it addresses.

```json title="Patch: replace the departments, leaving every other relationship unchanged"
{
  "relationships": {
    "parents": {
      "department": [{ "id": "95a6b7c8-3c4d-4e5f-8071-8293a4b5c6d7" }]
    }
  }
}
```

```json title="Patch: remove one custom label and record no subsidiaries"
{
  "relationships": {
    "parents": { "subsidiary": [] },
    "otherRelationships": { "networkMember": null }
  }
}
```

```json title="Patch: change the fiscal sponsor by ID and replace the DBA names"
{
  "relationships": {
    "fiscalSponsor": { "id": "d9e0f102-7081-4c93-a4b5-c6d7e8f90a1b" }
  },
  "dbaNames": ["Riverside Arts"]
}
```

| In a patch                     | Effect                                                                    |
| ------------------------------ | ------------------------------------------------------------------------- |
| An array for one kind or label | Replaces that array only. Other kinds, labels, and singular links remain. |
| `[]`                           | Leaves a present, empty collection.                                       |
| `null`                         | Removes the addressed kind, label, link, or the whole container.          |
| An object for a singular link  | Merges into the current reference.                                        |

A target in a patch needs only its `id`. If the sender also supplies a `name` or `identifiers`, the provider checks them against the target. There's no append or merge-by-ID: to add a department, send the full department array. Two writers changing the same kind at the same time can still overwrite each other.

## Reading every parent

Because each kind is its own property, a consumer that wants every containing organization flattens the standard kinds and the custom labels into one list of labeled edges:

```ts
type OrgRef = { id: string; name: string };
type Targets = OrgRef[] | null;
type OrgParents = {
  parent?: Targets;
  department?: Targets;
  chapter?: Targets;
  subsidiary?: Targets;
  otherParents?: Record<string, OrgRef[]> | null;
};

function parentEdges(parents?: OrgParents | null) {
  const { otherParents, ...standard } = parents ?? {};
  return [
    ...Object.entries(standard),
    ...Object.entries(otherParents ?? {}),
  ].flatMap(([kind, targets]) =>
    (targets ?? []).map((target) => ({ kind, target })),
  );
}
```

Following those edges from record to record walks the hierarchy. With several parents allowed, a walk can branch and reach the same ancestor more than once.

## What the schema does not check

The published schema checks shape: which properties exist, which values are arrays, and that every target in a read, and every target in an array a patch replaces, has an `id`. A singular reference in a patch, such as `fiscalSponsor`, merges into the current one, so it can leave `id` out. The schema cannot check facts about other records. The system that holds the organization is expected to:

- resolve each target, refresh its name and identifiers, and remove stale ones;
- refresh metadata kept from a previous singular target before validating, so an ID-only change succeeds;
- reject, as a whole, a patch with an unresolved target or contradictory metadata from the sender, including when a queued change is accepted later;
- reject links to the organization itself and repeated identical links;
- check for hierarchy cycles across kinds, and for successor and duplicate cycles separately, within the records it knows about.

A system can only check the records it knows about, so these checks don't cover the whole cross-system graph. Some conclusions also can't be drawn from data alone. A missing or unmatched target doesn't show that an organization doesn't exist. A shared name or address doesn't show containment or a duplicate, a payee designation doesn't show sponsorship, and a rename doesn't show succession.
