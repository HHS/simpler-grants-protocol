The [CommonGrants FastAPI template](https://github.com/common-grants/cg-api-template-fastapi) is a working CommonGrants API that you run first and then point at your own data. It serves the three opportunity endpoints from bundled sample data, validates every request and response with the [`common-grants-sdk`](https://pypi.org/project/common-grants-sdk/) Pydantic models, and generates an OpenAPI 3.1 document from those same models, browsable in Swagger UI. It is built with [FastAPI](https://fastapi.tiangolo.com/).

## Prerequisites

- **Python 3.11 or newer.** The template's CI runs on 3.11, the version in its `.python-version` file.
- **[Poetry](https://python-poetry.org/) 2.x**, the template's dependency manager.
- **make**, the command runner. Every target is a thin wrapper around a Poetry command.

No credentials, database, or other infrastructure are required.

## Get started

<Steps>

1. Open the [template repository](https://github.com/common-grants/cg-api-template-fastapi) on GitHub and click **Use this template** to create your own repository from it.

2. Clone your new repository:

   ```bash
   git clone https://github.com/<you>/<your-api>.git
   cd <your-api>
   ```

3. Check your versions:

   ```bash
   python3 --version # must report 3.11 or newer
   poetry --version  # must report 2.x
   ```

4. Install the dependencies:

   ```bash
   make install
   ```

   If Poetry picks up an older Python, point it at a newer one first with `poetry env use python3.11`.

5. Check that everything works before you change anything:

   ```bash
   make ci
   ```

   This runs the format, lint, and type checks, then the test suite with coverage.

6. Start the server:

   ```bash
   make dev
   ```

7. Open `http://localhost:8000/docs` to browse the API in Swagger UI and try a request from the browser.

8. Or, in another terminal, make a few requests with `curl`:

   ```bash
   # A page of opportunities, most recently modified first
   curl 'http://localhost:8000/common-grants/opportunities?pageSize=2'

   # Filtered and sorted search
   curl -X POST http://localhost:8000/common-grants/opportunities/search \
     -H 'Content-Type: application/json' \
     -d '{"filters":{"status":{"operator":"in","value":["open"]}},"sorting":{"sortBy":"title","sortOrder":"asc"}}'

   # The OpenAPI 3.1 document, generated from the same models
   curl http://localhost:8000/openapi.json
   ```

</Steps>

  - data/
    - opportunities.json # The bundled sample data
  - scripts/
    - generate_openapi.py # The OpenAPI export behind `make gen-openapi`
- tests/ # pytest suites: app, routes, fixtures, OpenAPI

</FileTree>

## How the pieces fit

The template, the SDK, and your extensions each own one layer:

- **The template owns HTTP.** The FastAPI routes parse and validate requests, shape error responses, and serve the OpenAPI document at `/openapi.json`.
- **The SDK owns the schemas.** The request, response, and opportunity models come from `common-grants-sdk`. The routes validate every response body against them before it is sent, and the OpenAPI document is generated from them, so the API and its documentation follow the published protocol.
- **Custom fields extend the opportunity model in one file.** If your data carries fields the protocol does not define, add them with `with_custom_fields`.
- **A plugin packages those extensions for reuse.** When other services or clients need the same custom fields and mapping, a plugin carries them.

### Add custom fields

`src/common_grants/schemas/opportunity.py` is the single definition of the opportunity model. The response models, the repository's types, and the OpenAPI document all read from it, so extending it extends all of them at once:

```python title="src/common_grants/schemas/opportunity.py"
"""
The single opportunity model this API serves.

Every route, response model, fixture parser and test reads `Opportunity` from
here, so this is the one place to add custom fields. See PORTING.md section 6.
"""

from common_grants_sdk.extensions.specs import CustomFieldSpec
from common_grants_sdk.schemas.pydantic import CustomFieldType, OpportunityBase
from pydantic import BaseModel


class LegacyId(BaseModel):
    """The value of the legacyId custom field."""

    system: str
    id: int


class Opportunity(
    OpportunityBase.with_custom_fields(
        custom_fields={
            "legacyId": CustomFieldSpec(
                field_type=CustomFieldType.OBJECT,
                value=LegacyId,
                description="Maps to the opportunity_id in the legacy system",
            ),
            "category": CustomFieldSpec(
                field_type=CustomFieldType.STRING,
                value=str,
                description="Grant category",
            ),
        },
        model_name="Opportunity",
    ),
):
    """The opportunity model this API serves."""
```

A custom field of the wrong type is now rejected when the record is parsed, and both fields appear in the opportunity response definitions in `/openapi.json`. Routes, handlers, and the repository protocol are untouched. Keep the `class` statement rather than assigning the result to `Opportunity`: the class keeps `Opportunity` a type, so the template's type check passes.

For more on defining and reading custom fields, see the [custom fields overview](/custom-fields/overview/).

### Share extensions as a plugin

`with_custom_fields` extends the one model this API serves. A plugin, built with the SDK's `define_plugin`, packages custom fields, custom search filters, and transforms between your source system's records and CommonGrants models as a typed Python package. Other services built on the same source system, and clients that consume your API, can then import it instead of redefining the same mapping. See the [Python SDK extensions guide](https://github.com/HHS/simpler-grants-protocol/blob/main/lib/python-sdk/common_grants_sdk/extensions/README.md) to build and publish one, and the [plugin catalog](/plugins/) for published plugins.

## Connect your own data

The bundled sample data sits behind a three-method repository protocol, `list`, `get`, and `search`, defined in `src/common_grants/services/repository.py`. Implement that protocol against your database or upstream API, wire your class into `src/common_grants/api.py`, and the routes, validation, and OpenAPI document keep working unchanged. The template's [`PORTING.md`](https://github.com/common-grants/cg-api-template-fastapi/blob/main/PORTING.md) is the walkthrough, covering stable ids, date and money handling, custom fields, and which tests to keep.
